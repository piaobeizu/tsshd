# Shared-bottleneck control latency: router/qdisc deployment

This is an **operator recipe**, not a tsshd input-path fix. In the tsshd#1 control-latency measurements, a saturated **single FIFO for both directions** delayed the small client input packet by 667–1240 ms in committed runs (0.7–1.6 s across reported repeats); a full 1000 × 1400-byte queue at 2 Mbit/s could take roughly 5.6 s to drain. With separate directional queues, input reached the server in about 51 ms (the configured one-way transit). These are harness conditions, **not** an Internet/WiFi SLA; 20% loss, burstiness and KCP retransmission also affect perceived confirmation. See [the design and evidence](weak-network-agent-design.md), §1 and §3 P5. Delivery of Ctrl-C and visible confirmation are different metrics: the latter can still sit behind already queued PTY output even when input is fast.

## Who owns the bottleneck?

The queueing node must be identified **before** installing a policy. Often it is the **user's router/AP**, not either tssh endpoint; it might be a single-queue shaper or VPN concentrator. The operator needs administrative control of that node's *actual congested egress / ingress shaper*. A qdisc on an uncongested tsshd server NIC cannot reorder packets already stuck at a remote AP. Find the direction, device, hardware offload and rate with counters under simultaneous flood + input; preserve existing firewall, QoS and traffic isolation policies. Do not paste these commands onto a production interface. Linux software qdiscs cannot schedule the physical half-duplex WiFi airtime themselves unless the AP/driver exposes a controllable scheduler and traffic actually traverses it.

**First choice:** give the two directions independent queues/shapers at the owner, with uplink headroom for small input and KCP ACKs. A split 2 Mbit/s-per-direction test does *not* represent a shared 2 Mbit/s aggregate cap; assess link capacity independently. If both directions must share one software shaper, use a **single parent rate** with bounded small-packet priority underneath. This is *intended* to protect small-packet latency under bulk load — the veth smoke test below checks wiring and size classification, not a measured latency win — but small packets sent by any flow can consume the reservation; authenticate/limit who may use it. Queue policy will not clear in-flight KCP/smux output or PTY input buffered ahead of Ctrl-C.

### Reproduce the queue topology locally

From the repository root on a disposable Linux host with `iproute2` (`ip`, `tc`), `ping` (iputils) and `sysctl` (procps), and IFB support. Run it as root: the script checks `EUID` 0 itself, and plain `CAP_NET_ADMIN` does not survive the `ip netns exec` + IFB sequence on typical distributions:

```sh
bash docs/shared-bottleneck-veth.sh shared
bash docs/shared-bottleneck-veth.sh split
bash docs/shared-bottleneck-veth.sh priority
```

The script creates two veth-linked endpoints and a forwarding router namespace, redirects **both router ingresses to one IFB** in `shared`/`priority`, and to **separate IFBs** in `split`. `shared` uses one 2 Mbit/s, 50 ms, 1000-packet `netem` FIFO (both directions); `split` uses two independent 2 Mbit/s, 50 ms FIFOs. `priority` uses one HTB parent capped at 2 Mbit/s, separate short/bulk queues (50 ms each) and a small-packet filter. Every device (veth pairs, IFBs) is created inside those three temporary namespaces — no interface is ever created in the host namespace, including on failure paths — and a stale same-named namespace left by a crashed run makes the script refuse to start; `trap` cleanup deletes only namespaces the invocation itself created. IPv6 is disabled inside the router namespace so the asserted class counters stay deterministic: kernel-generated IPv6/MLD packets would otherwise egress the IFBs and land in the HTB default class (the size filter is IPv4-only). It prints qdiscs, filter counters, smoke-tests two-way ping, and in `priority` mode probes the classification boundary with IPv4 total lengths 255 and 256 and asserts the class counters they land in (12 packets small, 4 bulk). The smoke test validates **wiring and size classification, not a latency improvement under load**. To establish that improvement, generate a reproducible bulk downlink flood and small uplink probes concurrently, compare p95/max one-way input delivery and goodput for all three modes, and check `tc -s` class/drop counters; use the project benchmark for controlled KCP/PTY confirmation metrics. No new measurement is asserted here. Do not reuse a benchmark README or baselines from tsshd#3/#5 as an ops recipe.

### What the priority filter actually does

The script's `tc filter ... u32 match u16 0x0000 0xff00 at 2 flowid 1:10` selects IPv4 **total IP length below 256 bytes** (high byte of the length field zero). The default HTB class receives the rest. The parent is capped at 2 Mbit/s; the high class has 128 kbit/s guaranteed with borrowing up to 2 Mbit/s, while bulk has 1872 kbit/s guaranteed and the same ceiling. These are *example budgets*, not tuned production values. Unlike one FIFO with `netem rate`, independent child queues allow the parent scheduler to choose the small class. A size filter is cooperative but not semantic: small bulk/ACK packets and other tenants qualify; large control datagrams and IPv6 do not. IP fragmentation, encapsulation, GRO/GSO, driver offload and non-IP traffic change what `tc` sees. For production, constrain by trusted interfaces/flow identity **as well as** size, extend explicitly for IPv6, police untrusted small-packet floods, and measure counters with real traffic. Never classify encrypted UDP by inner KCP payload size at a node that sees only an outer tunnel packet.

## DSCP and radio/tunnel boundaries

DSCP marking is **optional and default-off**. An endpoint marking its entire KCP UDP socket with EF (`IP_TOS` IPv4 or `IPV6_TCLASS` IPv6) would also mark bulk output/ACKs on that socket; KCP uses one UDP flow, so it cannot label Ctrl-C separately from data using socket-wide TOS. This is why this guide ships *no automatic marking flag*: marking all bulk as expedited can starve other traffic and can worsen a shared FIFO. Only consider a narrowly scoped opt-in client-uplink marking after measurements show that flow carries mostly control/ACKs, a trusted bottleneck owner maps it into a bounded priority class, and the user agrees to its network policy. DSCP alone does not change a FIFO without a cooperating scheduler.

* **WiFi:** DSCP-to-WMM user priority/access category mapping varies by AP, driver, OS and direction; EF is not guaranteed to land in the intended AC, and aggressive AC_VO can unfairly preempt voice or other stations. Airtime contention, retries and half-duplex scheduling can still dominate; verify mappings and radio-side airtime/queue stats on the actual AP.
* **VPN/tunnels:** the bottleneck may see only outer ESP/UDP/IP headers. Inner DSCP or packet size can be hidden; copying DSCP to outer headers is tunnel-specific and may violate provider policy. Classify at the tunnel ingress/egress you control, or apply a policy to the outer flow knowing it also includes bulk.
* **Middleboxes/ISPs:** DSCP is frequently zeroed, bleached, or remarked; test ingress and egress marking at each administrative boundary, not just `setsockopt` success. Avoid relying on markings across an untrusted Internet path.
* **Cellular:** modem/carrier radio bearers and scheduling are not necessarily controlled by Linux `tc` or public DSCP; the carrier may ignore marks. Endpoint qdiscs can bound offered load but cannot reorder the carrier's shared radio queue.

Finally, **P1 server output pacing is the primary remedy**: it reduces offered wire load and prevents the common queue from filling in the first place. This qdisc policy can help the remaining small input/ACK packets at a bottleneck you administer; it is a complement, not a substitute for pacing, and neither mechanism removes already ordered smux output or remote PTY input HOL.
